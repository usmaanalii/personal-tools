# Shared light style guide

`packages/design-tokens` owns foundation values (`--scale-*`) and their semantic light mappings (`--theme-*`). `packages/ui` owns reusable React controls and their styles. Apps own page composition, wording, requests and state. The production default is light. The catalogue demonstrates an alternate slate mapping; production dark mode remains future work. Quran content fonts, glyphs and canonical line layout remain source-specific.

Use the [adoption inventory](adoption.md) for current surfaces, states, exceptions and verification limits. Recheck the route entries and catalogue whenever a surface lands. The inventory is the gate before Quran branding exploration.

Import `@scratch-pages/ui/styles.css` in the app stylesheet and `Button` from `@scratch-pages/ui` in the connection view. The stylesheet supplies CSS variables and Tailwind utilities without Tailwind preflight. Vite uses `@tailwindcss/vite`; Next uses `@tailwindcss/postcss`. Both production builds must contain the complete shared `bg-ui-primary`, `text-ui-on-primary` and focus utility rules. Use literal utility class names so Tailwind finds them.

The adopted Button uses a native button. It has a visible focus outline, a disabled state and a 44px minimum height. Keep a text label on every connection action. Feedback belongs to each app: Playground exposes its JSON response and polite status; Next exposes an alert on failure and a status on progress/success. Preserve long-text wrapping. Reduced motion sets the shared transition duration to zero.

Playground home and route-loading shells also consume the default theme. The app owns native navigation links, destination headings and polite loading status. Tailwind utilities consume the shared surface, border, radius, shadow and motion variables. Document resets are conditional on the mounted shell. Keep prototype-specific selectors scoped so loading another tool's styles cannot change the home or demo presentation. Review style isolation, typography and spacing visually through the app and catalogue. Browser tests cover user journeys, accessibility and responsive fit.

The Quran chapter browser and surrounding chrome consume the shared Button, Input and ViewSwitcher. Verse actions and word-dialog close/previous/next actions also use Button. Button provides primary, outline and ghost variants plus default, icon and compact sizes; all retain at least 44px height. Input requires an app-supplied visible label. ViewSwitcher uses a labelled fieldset of native buttons with `aria-pressed`: every option is reached with Tab and activated with Enter/Space. The word dialog uses the owned shared Radix Dialog and Tabs wrappers. Its app owns the title, compact word summary, full-screen mobile layout, scrolling panels and focus policy. Word tabs use manual activation: arrows move focus and Enter/Space selects a panel. Latin verse text uses the shared body font at 16px. Arabic text retains its content-specific font, shaping and line height.

Apps use literal Tailwind utilities for ordinary presentation and responsive layout. Utility colours, fonts, spacing unit, radii, shadow and motion map back to the shared CSS variables; complete variant strings live in owned controls. Playground generates utilities once through `src/app/styles.css`, imported by its main entry. Next registers its sources in `globals.css`. Production scans exclude stories and tests, following [Tailwind's source detection rules](https://tailwindcss.com/docs/detecting-classes-in-source-files). Route stylesheets retain scoped baselines and content rendering without emitting utility copies: a later chunk's base utility could otherwise override an earlier responsive variant. The catalogue has its own source entry including stories and reuses the same theme definitions. Vite, Next and Storybook generate these styles without preflight. Keep Quran content rendering separate; Arabic glyphs, typography and word shaping remain app-local. See the [chapter state inventory](../../apps/playground/src/prototypes/quran/chapter-browsing-journeys.md) for visual changes and evidence limits and the [word-dialog verification](../../apps/playground/src/prototypes/quran/word-dialog-verification.md) for modal evidence.

State inventory: each connection begins idle, disables its action while loading, then displays a complete success or failure with another action available. The payload is atomic, so a partial-data state does not apply. Long returned content wraps within its region. Decorative icons, if added to owned controls later, should use `currentColor` and be hidden from assistive technology when a text label already names the action; icon-only actions need an accessible name. Do not add an icon dependency for the current text actions.

Storybook documents the default, loading/disabled, retry and long-label states plus the shared Dialog composition: `pnpm --filter @scratch-pages/ui storybook` for development or `build:storybook` for a static build. The stories have autodocs tags and prop descriptions, but no Docs addon is installed, so the catalogue currently exposes stories rather than a generated Docs page. The [live Storybook catalogue](https://usmaanalii.github.io/personal-tools/storybook/) is published through the combined Pages workflow and was verified on 2026-11-02. The #28 examples remain local until an approved push publishes them. See [the UI package README](../../packages/ui/README.md) for build and deployment instructions. The app smoke tests run axe and fail on violations across the loaded reader and within the open word dialog. Desktop/mobile journeys check responsive fit. Presentation checks separately resolve typography, pointer-target geometry and semantic theme mappings in a browser. Behaviour tests use accessible actions and outcomes.

## Extending the guide

- Reuse an owned control when its semantics, interaction and existing variants fit the action. Use native links for navigation. Give every icon action an accessible name.
- Add a variant when an existing control has the same semantics and behaviour but needs a recurring visual treatment demonstrated by a consumer. Keep complete literal utility strings in the owned control. Add its catalogue example and verify affected consumers.
- Keep a view app-local when its structure or content belongs to the feature. Chapter choices and saved-verse rows are compound content choices, not generic action buttons. Quran word targets preserve provider word shaping. These use native semantics and shared tokens without forcing the generic Button's text layout.
- Add a semantic token only for a named purpose that existing mappings cannot express. Keep its value and theme mappings in design-tokens. Do not create a token for every one-off content dimension or add arbitrary brand values during baseline adoption.
- Promote app-local presentation into shared UI when multiple real consumers need the same semantics and interaction. Move it with those consumers and catalogue coverage. Shared UI must accept data/actions from apps and must not import Quran state, APIs or fixtures.
- Keep feature behaviour in one owner when demonstrating composition. `VerseView` renders the production verse actions, words and translation. Its stacked and parallel-translation stories pass the same fixture data and callbacks; only layout utilities change. Neither layout nor theme has a production switcher.

## Catalogue demonstrations

`Foundations / Semantic themes / Comparison` renders the same Button, Input and ViewSwitcher under the default mapping and an alternate slate mapping. The optional `@scratch-pages/design-tokens/catalogue.css` import is confined to the story. Production apps import `styles.css` and retain the default theme.

`Playground / Quran / Verse reading` shows the production verse view stacked and with translation beside Arabic on wider canvases. Both collapse to a single column on narrow canvases. The app owns `VerseView`; generic UI imports no feature code. These examples demonstrate composition and token reuse, not a proposed Quran brand.

## Check ownership

Shared UI and token changes trigger Playground E2E, the Pages catalogue checks and Next's quality/production-browser checks. Pages owns the catalogue build and prefix-aware browser checks. Next builds its own consumer independently and does not repeat the catalogue build. The short Vitest app/function suites remain in Pages to gate publication and in Playground E2E to gate standalone verification. See [workflow ownership](../../.github/workflows/README.md#shared-style-guide).

For this catalogue's semantic-theme demonstration, compare a rendered shared control under both mappings. Different panel backgrounds alone do not establish that the control receives the alternate mapping. Confirm the check fails when that mapping is deliberately broken, then restore it. The reader composition checks must establish narrow stacking as well as viewport fit. A computed `font-family` comparison establishes the configured family list; it does not prove a web font downloaded or rendered.
